= Open Questions and Ambiguities

== Purpose

This document captures **missing information**, **ambiguities**, and **assumptions** made during mental model documentation creation.

== Architecture & Design

=== Q1: WiFi vs ML Conflict Resolution

**Question:** Why exactly do WiFi and ML features conflict in MicroPython on ESP32-S3?

**Context:** Documentation states "WiFi and ML features do not work together" but no technical root cause explained.

**Impact:** 
- Blocks camera/AI tool implementation
- Arduino port needed, but unclear why MicroPython can't be fixed
- Affects roadmap (v1.0 features)

**Found in:** `README.adoc`, `arc42/01-introduction.adoc`

**Assumption made:** Memory conflict between WiFi and TensorFlow Lite drivers. Need vendor confirmation.

**Needs clarification from:** UNIHIKER vendor or MicroPython ESP32 maintainer

---

=== Q2: MCP Protocol Version Upgrade Path

**Question:** What happens when MCP spec upgrades to v2.0 or later?

**Context:** Server hardcodes `MCP_VERSION = "2024-11-05"`. No version negotiation implemented.

**Impact:**
- Breaking changes in MCP might make server incompatible with new Claude Desktop
- No graceful degradation strategy
- Users stuck on old Claude version or forced update

**Found in:** `k10-mcp-server.py` line 23

**Assumption made:** MCP will maintain backward compatibility OR we'll need to support multiple versions

**Mitigation needed:** Version negotiation in `initialize` response, feature flags

---

=== Q3: Session Cleanup Strategy

**Question:** What is the intended session lifecycle? When should sessions expire?

**Context:** Sessions stored in RAM, never cleaned up. Documentation acknowledges memory leak but no defined policy.

**Impact:**
- After 100 connections → ~5KB wasted
- Unclear threshold for cleanup (1 hour? 1 day? Never?)
- Production deployment affected

**Found in:** `arc42/04-solution-strategy.adoc`, `arc42/11-risks.adoc`

**Assumption made:** Sessions should expire after 1 hour of inactivity OR limit to 10 most recent

**Needs decision:** Product owner / maintainer to define policy

---

=== Q4: Maximum Tool Count Before Performance Degrades

**Question:** How many tools can TOOLS array hold before JSON parsing becomes bottleneck?

**Context:** Currently 14 tools (~5KB JSON). At what size does `tools/list` response become problematic?

**Impact:**
- Roadmap includes camera tools, audio tools → could reach 30+ tools
- Large JSON → slow parsing on embedded
- Pagination not in MCP spec

**Found in:** `k10-mcp-server.py` lines 28-165

**Assumption made:** 50 tools is practical limit (~20KB JSON, ~100ms parsing)

**Testing needed:** Load test with 50+ tool schemas

=== Q6: I2C Bus Addressing

**Question:** What are actual I2C addresses for all sensors?

**Context:** Documentation mentions sensors exist but not their bus addresses. Needed for low-level debugging.

**Impact:**
- Cannot use logic analyzer effectively
- Hard to diagnose I2C conflicts
- Difficult to write alternative drivers

**Found in:** `arc42/05-building-blocks.adoc` (mentions I2C but no addresses)

**Assumption made:**
- AHT20 (temp/humidity): 0x38
- LTR-303ALS (light): 0x29  
- LIS2DW12 (accel): 0x19
- WS2812B (LEDs): Not I2C, custom protocol

**Verification needed:** Test with `i2cdetect` equivalent in MicroPython

---

=== Q7: Display Framebuffer Size

**Question:** How much RAM does display framebuffer consume?

**Context:** Documentation says "~20KB" but not measured precisely.

**Impact:**
- Affects total available RAM calculation
- Determines feasibility of double-buffering
- Important for memory management

**Found in:** `arc42/05-building-blocks.adoc`

**Assumption made:** 20KB based on screen resolution (320x240 @ 16-bit color ≈ 150KB, likely compressed)

**Measurement needed:** `gc.mem_free()` before and after `screen.init()`

=== Q8: LED Brightness Range Interpretation

**Question:** What do brightness levels 0-9 actually mean?

**Context:** `rgb.brightness(5)` sets brightness, but is this linear? PWM duty cycle? Log scale?

**Impact:**
- User expectation mismatch ("5 should be half of 9")
- Cannot document precisely
- Affects tool behavior consistency

**Found in:** `k10-mcp-server.py` line 187

**Assumption made:** Linear scale (0 = off, 9 = max, 5 ≈ 55% brightness)

**Testing needed:** Measure LED output with light sensor at each level

== Protocol & MCP

=== Q9: Streaming Response Support

**Question:** Does HTTP streamable transport require chunked transfer encoding?

**Context:** MCP spec mentions "streamable" HTTP but current implementation returns single JSON response.

**Impact:**
- Missing streaming capability (e.g., camera feed)
- Not fully compliant with "streamable" transport?
- Unclear if Claude Desktop expects chunked responses

**Found in:** `arc42/09-decisions/ADR-001-http-transport.adoc`

**Assumption made:** Single JSON response sufficient for current tools, streaming deferred to future

**Needs clarification from:** MCP spec authors or Claude Desktop team

---

=== Q10: CORS Headers Necessity

**Question:** Are CORS headers needed if Claude Desktop is local client (not browser)?

**Context:** Implementation adds `Access-Control-Allow-Origin: *` but unclear if required.

**Impact:**
- Unnecessary headers add bandwidth
- Security: wildcard CORS is permissive
- Might be artifact from web-based testing

**Found in:** `k10-mcp-server.py` lines 350-353

**Assumption made:** Needed for browser-based testing tools (Postman web, etc.), harmless to include

**Testing needed:** Remove CORS headers, test if Claude Desktop still works

---

=== Q11: Session ID Generation Algorithm

**Question:** What guarantees uniqueness of session IDs?

**Context:** Implementation uses `os.urandom(8).hex()` (16-char hex string).

**Impact:**
- Collision probability?
- Enough entropy for 100+ sessions?
- Security implications (predictability?)

**Found in:** `k10-mcp-server.py` line 356

**Assumption made:** 16-char hex = 64-bit entropy, sufficient for non-adversarial use case

**Calculation:** Birthday paradox: 1% collision after ~6 billion sessions (way more than needed)

**Low priority:** Current approach sufficient
