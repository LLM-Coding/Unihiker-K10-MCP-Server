== Key Concepts (Must Understand)

=== 1. MCP Protocol

Model Context Protocol - standardized way for AI assistants to discover and use tools.

* Based on JSON-RPC 2.0
* Tools discovered via `tools/list`
* Executed via `tools/call`

**Read:** link:arc42/08-concepts.adoc#concept-1[Concept: JSON-RPC as Universal Language]

---

=== 2. Stateless Tool Execution

Each tool call is independent. No state between calls.

* Set LED to red (absolute) ✅
* Toggle LED (relative) ❌

**Read:** link:arc42/08-concepts.adoc#concept-2[Concept: Stateless Tools]

---

=== 3. HTTP Transport Layer

Single `/mcp` endpoint for all MCP communication.

* Chose HTTP over SSE (reliability)
* Request/response model (no streaming yet)
* CORS-enabled for web clients

**Read:** link:arc42/09-decisions/ADR-001-http-transport.adoc[ADR-001: HTTP Transport]

---

=== 4. Hardware Abstraction Layer (HAL)

`unihiker_k10` module provides Python API for hardware.

* Vendor-supplied, binary, closed-source
* Treat as black box
* Always wrap in try/except

**Read:** link:arc42/08-concepts.adoc#concept-4[Concept: HAL as Black Box]

---

=== 5. Error Handling Philosophy

Never crash the server. Always return valid MCP response.

* Errors are data, not exceptions
* Use `{"isError": true}` in result
* Client sees helpful message

**Read:** link:arc42/08-concepts.adoc#concept-5[Concept: Error Handling]

== Component Architecture

```
Claude Desktop (Client)
    ↓ HTTP POST /mcp
HTTP Server (Microdot)
    ↓ parse JSON-RPC
Protocol Handler (handle_mcp_request)
    ↓ dispatch method
Tool Executors (execute_tool)
    ↓ HAL calls
Hardware Layer (unihiker_k10)
    ↓ I2C/SPI/GPIO
K10 Hardware (sensors, LEDs, display)
```

**Read:** link:arc42/05-building-blocks.adoc[Building Blocks View]

== Development Workflows

=== Adding a New Tool

1. Design tool schema (JSON Schema)
2. Add to `TOOLS` array
3. Implement in `execute_tool()`
4. Add error handling
5. Test with curl
6. Test with Claude Desktop

**Details:** link:arc42/08-concepts.adoc#pattern-1[Pattern: Adding New Tools]

---

=== Debugging an Issue

1. **Reproduce** with curl (isolate server from client)
2. **Check REPL** for Python tracebacks
3. **Add logging** to `execute_tool()`
4. **Consult guide** link:onboarding/common-issues.adoc[Common Issues]

**Details:** link:onboarding/development-workflow.adoc#debugging-workflow[Debugging Workflow]

---

=== Reviewing Code

**Checklist:**

- [ ] Functionality correct?
- [ ] Error handling present? (try/except)
- [ ] Schema matches implementation?
- [ ] Memory impact <10KB?
- [ ] Tested on hardware?

**Details:** link:onboarding/development-workflow.adoc#code-review-guidelines[Review Guidelines]

---

== Common Pitfalls

**Top 5 mistakes:**

1. ❌ Not wrapping HAL in try/except → server crashes
2. ❌ Forgetting `screen.show_draw()` → display doesn't update
3. ❌ Testing only with Claude → can't isolate issues
4. ❌ Loose tool schemas → Claude confusion
5. ❌ Storing state in globals → violates stateless design

**Read:** link:llm/antipatterns.adoc[Complete Antipatterns Guide]

== Maintenance

**Keeping docs current:**

1. **When adding feature:**
   - Update link:arc42/05-building-blocks.adoc[Building Blocks] if new component
   - Add ADR if architectural decision
   - Update tool count in link:arc42/01-introduction.adoc[Introduction]

2. **When fixing bug:**
   - Add to link:onboarding/common-issues.adoc[Common Issues] if recurring
   - Document workaround in link:arc42/08-concepts.adoc[Concepts]

3. **When changing architecture:**
   - Write new ADR in link:arc42/09-decisions/[09-decisions/]
   - Mark old ADR as superseded
   - Update link:arc42/04-solution-strategy.adoc[Solution Strategy]

4. **When questions answered:**
   - Move from link:open-questions.adoc[Open Questions] to appropriate doc
   - Update assumption validation

**Review cycle:** Quarterly (or before major releases)
