== System Vision and Purpose

The K10 MCP Server is an **embedded Model Context Protocol (MCP) server** that runs directly on the UNIHIKER K10, a comprehensive K12 STEM education board. The K10 is designed for teaching AI, IoT, and physical computing to students in grades 3-12.

**Hardware Overview:**

* **Processor:** ESP32-S3N16R8 dual-core Tensilica LX7 @ 240 MHz
* **Memory:** 512KB SRAM + 8MB PSRAM + 16MB Flash
* **Display:** 2.8" ILI9341 TFT (240×320 pixels)
* **Camera:** 2MP OV2640
* **Audio:** 2-microphone array + speaker (offline speech recognition)
* **Sensors:** AHT20 (temp/humidity), LTR-303ALS (light), LIS2DW12 (accelerometer)
* **Connectivity:** WiFi 2.4GHz, Bluetooth 5.0
* **Expansion:** Micro:bit-compatible edge connector, Gravity 3pin/4pin ports (DFRobot ecosystem)
* **AI Features:** 4 pre-installed TinyML models (Face Detection, Pet Recognition, QR Code, Motion Detection)
* **Programming:** Mind+ (block-based), MicroPython, Arduino (via Arduino IDE)

The MCP server enables AI assistants like Claude to control this integrated educational platform without an intermediate gateway computer.

[quote]
*Vision:* Bridge the gap between Large Language Models and physical IoT devices by implementing a standards-based protocol directly on resource-constrained embedded hardware.

=== Core Problem Solved

Traditional IoT control requires:

1. IoT Device ← Serial/API → Gateway Computer ← HTTP/WebSocket → AI Assistant

This architecture requires:
- Always-on gateway computer
- Complex middleware for protocol translation
- Network dependencies between multiple hops

*Our solution:* Direct connection

[source]
----
Claude Desktop ← HTTP/MCP → K10 Device (ESP32-S3)
                             ├─ RGB LEDs
                             ├─ Sensors
                             ├─ Display
                             └─ Camera
----

=== Why It Matters

1. **Educational Value:** Demonstrates MCP protocol on embedded devices
2. **Proof of Concept:** Shows MCP viability beyond desktop/server environments  
3. **Lower Barrier:** No gateway computer needed - just WiFi
4. **Real-time Control:** Direct hardware access with minimal latency

== Deprecation Plans

=== Upcoming Deprecations

[cols="1,2,2,1",options="header"]
|===
|Feature |Reason |Alternative |Timeline

|**SSE Transport**
|Overly complex for embedded, poor error handling
|HTTP streamable transport (already implemented)
|Deprecated v0.3, removal v0.5

|**Multi-endpoint design**
|Fragmented routes, harder to maintain
|Single `/mcp` endpoint handles all JSON-RPC
|Deprecated v0.3, removal v0.5

|**ujson module**
|Name compatibility issues with newer MicroPython
|Use `json` module directly
|Warning v0.4, migration v0.6
|===

=== No Longer Supported

* **Python 2.x syntax** (if any existed) - MicroPython 1.20+ required
* **Port 80 HTTP** - Use 8080 (unprivileged port, no root needed)

== Constraints

=== Technical Constraints

[cols="1,2,1",options="header"]
|===
|Constraint |Description |Impact

|**ESP32-S3 Memory**
|512KB SRAM + 8MB PSRAM, ~100KB SRAM available after OS (PSRAM for ML)
|Cannot implement full MCP spec (e.g., large resource streaming). PSRAM available but used by TinyML models.

|**MicroPython Limitations**
|No asyncio SSL, limited stdlib, slower than CPython
|No TLS support, must implement workarounds

|**WiFi vs ML Conflict**
|MicroPython on K10 cannot use WiFi + camera/TinyML simultaneously (driver/memory conflict)
|Need separate Arduino implementation to enable WiFi + AI features together. Hardware supports both, but not in MicroPython.

|**JSON-RPC Only**
|MCP spec allows JSON-RPC; we cannot do efficient binary protocols
|Higher bandwidth than necessary, but acceptable for low-frequency commands
|===
